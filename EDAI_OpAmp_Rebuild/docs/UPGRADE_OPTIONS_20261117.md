# 도구·최적화·공정 모델 도입 검토

검토만 진행했으며 spicelib, Optuna, 새 PDK를 설치하거나 기존 흐름에 연결하지 않았다.

## 역할 구분

| 항목 | 개선하려는 부분 | 자동으로 해결하지 않는 부분 |
|---|---|---|
| spicelib | 넷리스트/회로도 편집, 시뮬레이터 실행, raw/log 분석과 실행 관리 | 목표 선택, 적절한 회로 구조, 측정 정의의 정당성, 소자 모델의 물리 정확도 |
| Optuna | 우리가 정한 변수 범위와 목적함수 안에서 수치 파라미터 탐색 | 회로 지식과 제약의 자동 정의, 제조 가능한 설계의 자동 보장 |
| 공정 모델/PDK | 선택한 공정의 소자 특성과 지원 조건을 반영한 설계·검증 | 틀린 시험 조건/판정 코드의 수정, 모든 잡음·mismatch·레이아웃 항목의 자동 검증 |

spicelib의 공식 명칭은 spicelib이며 LTspice 외에도 ngspice 등의 실행 클래스를 제공한다.
현재 자체 실행/분석 코드가 이미 있으므로 전면 교체보다 하나의 실행 어댑터에서 등가성을 먼저 평가하는 편이 적절하다.
우리가 만든 실행 계약, 검사 계획, 물리적 판정·한계 분류는 계속 유지해야 한다.

## Optuna를 도입한다면

LLM: 토폴로지, 초기 설계, 합리적인 탐색 변수/범위와 제약 제안, 탐색 정체 시 구조·범위 재검토.

Optuna: 정해진 변수와 범위 안에서 다음 파라미터 조합 제안.

검증 시스템: 변경한 소자값을 적용한 회로 생성, 계획과 실제 조건 대조, 시뮬레이션, 측정, 실패/미검증 분류.

처음에는 차동쌍·전류 미러의 대칭을 유지하는 변수 묶음과 전류/보상값 등 소수 변수로 시작한다.
수십 개 소자를 모두 독립 변수로 취급하거나 매 시행에 모든 조건을 실행하지 않는다.
기본 동작 및 주요 성능으로 후보를 선별하고 최종 후보는 원래 전체 조건으로 검증한다.
미실행·모델 미검증·측정 오류를 만족한 사양으로 점수화하면 안 된다.

성능 비교 후보는 LLM 기반 수정, 동일 초기 회로에서의 Optuna 수치 조정, LLM+Optuna 결합이다.
초기 회로·모델·목표·시뮬레이션 예산·종료 기준을 통제해야 한다.
토큰이 줄어도 시뮬레이션 수가 늘 수 있으므로 비용/시간/성공률을 함께 평가해야 한다.
도구 추가 자체보다 이 역할 분담이 어떤 문제에서 유리한지 검증하는 것이 프로젝트의 결과가 된다.

## 공정 모델과의 순서

현재 목적이 AI 설계·피드백 구조의 비교라면 일반 모델에서도 작은 Optuna 실험은 가능하다.
실제 공정에서 유효한 IC 설계 결과를 주장하려면 해당 공정 모델과 적용 범위를 정한 뒤 본격 사이징해야 한다.
일반 모델에서 찾은 최적값이 공정 모델에서도 최적이라고 가정하지 않는다.

현재 TL071C의 30V 조건을 SKY130 1.8V 소자로 단순 치환할 수 없다.
선택한 소자의 단자별 지원 전압에 맞는 설계 과제와 사양 적용 범위를 따로 정해야 한다.
기존 데이터시트 조건을 몰래 낮추지 않고, 공정에 맞는 별도 과제로 구분한다.
Sky130은 ngspice 호환 SPICE 모델을 제공하지만, 전환은 모델명 변경 하나로 끝나지 않는다.
소자 인스턴스, 단위·파라미터, behavioral 식, 해석/측정 명령, raw/log 형식과 기준 회로 재검증을 검토해야 한다.

추천은 현재 검사 신뢰성 마무리 → 일반 모델의 작은 Optuna 파일럿 → 목적에 맞는 공정 모델 과제로 확대다.
실제 공정 설계가 즉시 최우선 목표라면 두 번째 단계보다 공정/전원 범위 정의를 먼저 진행한다.
spicelib은 필요한 편집·실행·결과 읽기 기능부터 선택적으로 비교한다.
