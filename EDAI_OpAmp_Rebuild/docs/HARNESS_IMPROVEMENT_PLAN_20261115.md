# 하네스 개선 대상 선정 — 2026-11-15

후속 구현: 이 문서의 첫 개선 가설에 해당하는 범위·상세 근거 전달을 로컬 코드에 반영했다. [구현 및 검증 기록](FEEDBACK_CONTRACT_V2.md)을 참고한다. 아래 내용은 변경 전 분석 기록이다.

이번 작업은 현재 지침, 실제 설계 요청, 에이전트 응답, 원본 검증 대장의 정적 대조입니다. 런타임 코드·지침·기존 실험 결과를 변경하지 않았고 새 시뮬레이션/모델 호출/비교를 실행하지 않았습니다.

## 제안하는 첫 개선 가설

**모델·검사기 한계와 현재 후보의 측정 성립 실패를 구분하고, 필수 미해결 항목과 그 실제 근거를 명시적으로 전달하면, 설계자가 필요한 목표를 보류하거나 유효하지 않은 수치를 성능값으로 해석하는 오류를 줄일 수 있다.**

수치가 빠져 있어 목표를 모르는 문제는 아닙니다. 요구 수치·측정값·전원/부하 조건은 이미 전달됩니다. 우선 개선할 것은 상태의 의미와 세부 판정 근거 전달입니다. 물리적 실패 원인을 자동 확정하는 기능이나 Harness²가 아닙니다.

## 확인된 사항

### 1. 고정 지침과 기본 제공 내용의 중복

fixed_v1은22개 규칙입니다. C2(5), C4(4), C8(2)의11개는 인터페이스/실행 계약과 호스트 역할 중심입니다. 문법/모델/포트/변경 금지/JSON 형식은 기본 조건에도 상당 부분 존재하고 코드도 강제합니다. 나머지 설계 관련 지침은 조건부 검토 원칙이지 이번 실패에 맞춘 수치적 수정법은 아닙니다.

이 규칙들이 불필요하다는 뜻은 아닙니다. 다만 기존 비교에서 실질적으로 더해진 설계 판단 정보가 얼마나 있었는지 구분해야 합니다. 기본 모델이 모든 규칙을 이미 알고 있다는 사실까지 확인한 것은 아닙니다.

### 2. 현재 회로 때문에 판정 불가인 항목과 구현 한계가 섞여 보임

호스트는 qualified_measurement_families와 scope_case_ids로 이번에 충족해야 하는58조건을 알고 있습니다. 나머지22조건은 현재 모델/검사기 한계로 미검증입니다.

그러나 실제 설계 요청에는 그58조건의 명시적 목록이나 사례별 평가 범위 역할이 없습니다. 요구사항/80개 상태와 설명은 들어 있지만, 호스트가 사용하는 성공 범위와 연결된 표시는 별도로 전달되지 않습니다.

실제 초기80pF의36V tOR(CASE-795b1f61285290aab15c)은 구현된 필수 검사인데도 현재 후보에서 포화/해제 조건이 성립하지 않아 unverified_adapter로 기록됐습니다. 정말 미구현인 검사도 같은 계열 상태를 사용합니다. reason 문장이 있으므로 구분 정보가 완전히 없는 것은 아니지만 구조적인 범위/상태 구분이 부족합니다.

C1-2의 'Unknown/model-limited cases remain unknown'도 현재 후보의 성립 실패까지 계속 보류하라는 뜻으로 읽힐 여지가 있습니다. 현재 모델의 근본 한계와 현재 후보의 측정 미완료를 분리하는 문장이 필요합니다. 모든 미검증을 통과시키거나 모델의 능력을 임의로 확대해서는 안 됩니다.

### 3. 원본에 있는 실패 근거가 전달에서 빠짐

36V tOR 원본 parts에는 high/low 각각 다음이 있습니다.

- gate: Overload state not sufficiently stationary in declared hold window.
- 포화 관측 구간의 출력 변화 폭: high2.16245V / low2.86476V.
- 현재 코드의 허용 변화 폭: 전원0.02배,36V에서는0.72V.

실제 입력의 top-level gate_issues는 빈 배열이고, parts의 gate와 overload_evidence는 make_request가 전달하지 않습니다. 시험 profile은 전달되지만 실제로 성립하지 않은 이유의 세부 근거는 빠집니다. 현재 VCM 오류의 measurement_coverage와 numerical_attempts도 별도 구조로 전달하지 않고 오류 문자열에 주로 의존합니다.

tOR의 약23.99/23.28µs 값은 원본에 존재하고 입력에도 전달됩니다. 하지만 포화 정상 상태가 성립하지 않았으므로 정규 성능 판정값으로 확정해 쓰면 안 됩니다. 진단용 수치라는 역할을 명시하는 편이 좋습니다.

### 4. 에이전트 응답에서 관찰한 것과 한계

기본 에이전트는36V 사례를 가설과 성립 확인 계획에 포함했습니다. 지침 에이전트의 가설 목록에는 이 사례가 없고, tradeoffs에서 미확정36V 프로토콜 등에 대해 해결을 주장하지 않는다고 적었습니다.

이는 지침 에이전트가 필수 목표를 영구 제외했다고 증명하지 않습니다. 검증 전 해결을 주장하지 않는 정직한 표현일 수도 있습니다. 실제 두 수정안 모두 이후 해당 프로토콜을 성립시켰고, 회복시간 자체가10µs를 넘어 미달했습니다. 따라서 빠진 근거/모호한 상태가 최종 미달의 물리적 원인이라고 결론 내리지 않습니다.

## 구체적인 변경안 — 아직 구현하지 않음

### 공통 계약으로 먼저 명확히 할 내용

양쪽 조건에 같은 필수 범위58조건과 현재 한계22조건을 제공해야 합니다. 기본 조건에서 목표 정보를 숨겨 개선군에 유리한 비교를 만들지 않습니다. 모델 한계/미구현은 현재 범위의 미검증으로 유지합니다. 실행 오류는 물리적 사양 미달과 분리합니다.

### 평가할 개선 요소 하나

같은 원본 검사 근거로 만든 **필수 미해결 항목 요약**을 제안합니다. 사례마다 다음을 연결합니다.

| 정보 | 의미 |
|---|---|
| case_id 및 필수 범위 여부 | 이번 성공 조건에 포함되는가 |
| 현재 상태의 종류 | 성능 미달 / 시험 성립 실패 / 실행 미완료 / 현재 구현 한계 |
| 수치의 유효성 | 정규 성능 판정값인지, 진단 참고값인지 |
| 실제 실패 근거 | parts의 gate, 판정 기준, 측정된 변화 폭 등 |
| 다음에 필요한 확인 | 같은 고정 조건에서 재검증, 실행 진단 등. MOS 수정값을 정답으로 지정하지 않음 |

36V 예시는 '검사가 없는 항목'이 아니라 '필수 검사이지만 현재 후보의 포화 상태가 충분히 안정되지 않아 정규 판정이 미완료'라고 전달합니다. 테스트 시간을 임의로 늘리거나 조건을 바꾸도록 유도하지 않습니다.

설계 지침에는 현재 모델의 불가능 항목과 현재 회로의 미완료 항목을 구분하는 문구를 넣습니다. 요청 생성기는 이미 저장한 사실만 옮기고 물리적 원인을 생성하지 않습니다.

## 확인 순서와 성공 기준

1. 먼저 저장된 데이터만으로 입력 완전성을 검사합니다. 원본의 필수 사례·gate·관측값이 빠지지 않는지, 무효 수치가 합격 판정으로 사용되지 않는지 확인합니다. 이 단계는 소프트웨어 정확성 검사이며 성능 향상의 근거는 아닙니다.
2. 고친 성공 범위 계약은 기본/개선 조건에 공통 적용합니다. 서로 같은 원본 목표와 근거에 접근하도록 하고, 개선군에만 그 근거를 정리한 요약/행동 지침을 추가하는 비교를 제안합니다. 새 진단 데이터를 추가한다면 단순 문장 효과가 아니라 정보 추가 효과라는 점을 명시하거나 분리해 비교해야 합니다.
3. 같은 모델 설정·초기 회로·수정/EDA 예산에서 비교합니다. 필수 항목을 잘못 제외하거나 판정 불가 값을 유효 성능으로 취급하는지 확인합니다.
4. 실제 성공률/미달폭/수정 횟수와 기존 통과의 회귀를 평가합니다. 항목을 언급했거나 형식을 잘 지켰다는 사실만으로 설계가 좋아졌다고 주장하지 않습니다. 실패나 무효과도 그대로 남깁니다.

과제/반복 수와 예산은 아직 확정하지 않았으며 새 실험은 시작하지 않았습니다. 현재 단회 결과만으로 이 가설의 효과를 입증할 수 없습니다.

## 우선 보류할 다른 개선 후보

- 과거 변경/측정 이력: 상태에는 있지만 요청 파일에는 현재 후보 중심으로 전달됩니다. 다만 이전 두 번 실험에서 같은 에이전트는 자기 대화 이력을 유지했고 최신 실험은 단회여서, 이력 누락을 현재 실패 원인으로 단정하지 않습니다.
- best 평가 점수: 현재 [0,미통과수] 중심으로 같은 미달 수의 개선 폭은 구분하지 못합니다. 실제 다른 두 조건의13.12/14.55µs가 같은 미달 개수인 예가 있습니다. 이를 보완한다면 공통 평가기 정확성/선택 정책과 설계 지침 효과를 구분해야 하며, 이번 분석에서는 코드를 바꾸지 않았습니다.
- 내부 노드/gm 등 추가 진단: 현재 몇몇 probe는 별도 경로입니다. 신규 시뮬레이션을 추가하면 진단 예산을 통제해야 하므로 첫 변경에 함께 넣지 않습니다.
