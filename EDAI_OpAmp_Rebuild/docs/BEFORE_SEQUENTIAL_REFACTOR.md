# 이전 비교 방식의 기록 — 현재 주 실행 경로가 아닙니다

# EDAI Op-Amp Pipeline — 단계별 재구성 시작본

기존 AnalogVerifier는 보존하고 별도 폴더에서 다시 구성하고 있습니다. 현재 구현 범위는 **PDF 전체 탐색 → 후보 페이지 지도 → 이미지 변환 → Nemotron 파싱 → 구조 검사 → 코드/수동 사양 후보 → 원본 수치 대조 → 근거 통합**까지입니다. 외부 LLM 자동 추출과 HKG 생성은 아직 연결하지 않았고, 조건 의미·전체 문서 누락 검증도 완료 전입니다.

## 이름 규칙

`파트_파트내순서_동작.py`를 사용합니다. 숫자와 함께 기능도 이름에 넣어 파일명만으로 역할을 파악합니다. 전체 실행 순서는 실행 파일과 이 문서에 명시합니다. 같은 파일 안의 임의 번호 함수로 순서를 숨기지 않습니다.

| 상태 | 파일 | 입력 → 출력 | 책임 |
|---|---|---|---|
| 구현 | `opamp_pipeline/pdf_01_inventory.py` | PDF → 전체 페이지 텍스트·책갈피·품질 신호 | 문서 열기·전체 조사. 이미지/AI 없음 |
| 구현 | `opamp_pipeline/pdf_02_page_plan.py` | 조사 결과 + 제품명 → 후보 페이지 지도 | 페이지 역할·선택 근거 기록. 최종 제외 확정 아님 |
| 구현 | `run_pdf_overview.py` | 실행 옵션 → 단계별 저장 파일 | 위 두 단계 실행·결과 저장 |
| 구현 | `opamp_pipeline/pdf_03_render_pages.py` | 후보 페이지 → PNG·이미지 매니페스트 | 원본 해시와 페이지·이미지 좌표계 연결, 이미지 재사용 |
| 구현 | `opamp_pipeline/pdf_04_parse_layout.py` | PNG → 페이지별 파싱 JSON | Nemotron 호출·원본 응답/배치 보존·실패 기록·재시작 |
| 구현 | `run_pdf_layout.py` | 저장된 단계 1~2 결과 → 단계 3~4 실행 | 키는 환경변수 또는 지정한 .env에서 읽고 결과에 저장하지 않음 |
| 구현 | `opamp_pipeline/pdf_05_check_layout.py` | 페이지 결과 → 구조 검사 보고 | 빈 응답·잘림·출처·표 머리글 불일치 감지. 사양 정확성 보증 아님 |
| 구현 | `opamp_pipeline/spec_01_extract_rows.py` | 원본 표 → 셀 근거 / 수동 JSON → 사양 후보 | 코드 셀 추출과 수동·향후 API 추출기 경계를 분리 |
| 구현 | `run_spec_candidates.py` | 저장 결과 + 수동 JSON → 구조 검사와 후보 저장 | 외부 LLM 호출 없음 |
| 구현(부분 검증) | `opamp_pipeline/spec_02_verify_sources.py` | 사양 후보 + 코드 근거 + 원본 → 대조 보고 | 수치·열·단위·행 연결/누락 확인. 조건 의미·전체 문서 완전성은 미확인 |
| 구현 | `opamp_pipeline/spec_03_merge_evidence.py` | 두 후보 + 검증 보고 → 근거 통합 JSON | 일치한 값·의미 후보·미검증 상태 보존, 충돌은 확정값으로 채택하지 않음 |
| 구현 | `run_spec_verification.py` | 저장된 입력 → 원문 대조·통합 실행 | API 호출 없음 |
| 향후 | `hkg_01_build_graph.py` | 확인된 사양·핀 → HKG | 구조화, 새 사양을 임의로 만들지 않음 |
| 향후 | `verify_01_plan_tests.py` | 확정 목표 → 검사 계획 | 미지원/미검증 구분 |
| 향후 | `pdg_01_plan_signals.py` | 핀·관계·시험 조건 → 인가 일정 | 원문 시간과 추정 시간을 구분 |
| 향후 | `design_01_run_loop.py` | 목표·검사·지침 → 설계 반복 | Hermes 역할과 모델 호출 관리 |

‘향후’ 파일은 설계안이며 아직 존재하거나 연결된 코드가 아닙니다. 하네스² 지침 비교도 아직 이 새 프로젝트에 구현하지 않았습니다.

## 실행

Python 환경에 `requirements.txt`를 설치한 후:

```powershell
python run_pdf_overview.py --pdf "원본 PDF 경로" --target LM358B --output "결과 폴더"
```

- `01_pdf_inventory.json`: 모든 페이지의 텍스트·단어 좌표·회전/크롭 정보·책갈피·품질 신호 및 파일 해시. 로컬 근거 보관용이며 AI에 자동 전달하지 않음
- `02_page_plan.json`: 대상 제품별 후보 페이지·근거·재확인 표시
- `OVERVIEW.md`: 사람이 확인할 요약

첫 두 단계는 API 키 없이 실행되며 PDF를 이미지로 만들지 않습니다. 스캔본·글자 깨짐·미분류 페이지는 확인 대상으로 남깁니다. 관련성이 낮아 보이는 페이지도 원문 목록에서 삭제하지 않습니다.

페이지 계획에는 전체 원문과 단어 좌표를 복사하지 않습니다. 단계 4는 선정된 이미지와 파싱 옵션만 NVIDIA API에 전송합니다. 전체 문서 텍스트·단어 좌표·API 키는 분석 본문에 포함하지 않습니다. 아직 후단 LLM에는 아무 정보도 보내지 않습니다.

## 이미지 변환과 Nemotron 파싱 실행

```powershell
python run_pdf_layout.py --run-dir "단계 1~2 결과 폴더" --env-file "NVIDIA_API_KEY가 있는 .env 경로"
```

이미지만 만들려면 `--render-only`를 사용합니다. 키가 환경변수에 있으면 `--env-file`은 생략할 수 있습니다. 키를 코드·공유 ZIP에 넣지 않습니다.

- `03_render_manifest.json`: 요청 페이지, 원본/이미지 해시, DPI, 이미지 크기, 회전 정보. 기본은 핵심·참고 후보를 처리하며 재확인 전용 페이지는 pending 목록에 보존합니다.
- `images/`: 150 DPI RGB 이미지. 한 페이지가 여러 역할을 가져도 하나만 생성합니다.
- `pages/page_XXXX.json`: Nemotron API 원본 응답과 텍스트·클래스·좌표. 실패도 같은 위치에 기록합니다.
- `04_parse_summary.json`: 완료·실패·재사용 페이지와 호출/토큰 기록. 각 페이지 완료 시 갱신합니다.

같은 명령을 다시 실행하면 원본/이미지 해시와 호출 설정이 일치하는 성공 결과를 재사용합니다. 실패 결과는 다시 시도합니다. 출력 한도에서 잘린 응답은 성공으로 집계하지 않으며 원본 응답은 보존합니다. 저장된 텍스트/곡선/도식은 아직 정확성 검증 전 결과로, 자동 그래프 수치화나 회로 연결 추출을 완료했다는 의미는 아닙니다.

## 구조 검사와 현재의 수동 사양 JSON

```powershell
python run_spec_candidates.py --run-dir runs/lm358b_overview_20261112 --manual-json manual_inputs/lm358b_assistant_candidates.json
```

- `05_layout_checks.json` / `.md`: 전체 파싱 후보의 구조 검사. 현재 6~7쪽은 LaTeX 열 수와 머리글이 맞지 않아 재확인 표시가 있습니다.
- `06_extraction_packet.json`: 현재 추출에 사용하는 5·6·7·26쪽의 텍스트만 모은 입력. 원본 전체 좌표는 포함하지 않습니다.
- `06_spec_candidates.json`: 채팅 AI가 작성한 사양 후보. 형식·중복 ID·출처 해시를 코드로 검사합니다. 전체 사양 정확성은 확정되지 않았으며 최신 부분 검증/통합 결과는 단계 7~8 파일에 있습니다.
- `manual_inputs/lm358b_assistant_candidates.json`: 이번에 채팅 AI가 작성한 원본 수동 입력. 특정 제품의 데이터 파일이며, 제품별 값을 하드코딩한 범용 추출 알고리즘이 아닙니다.

현재 JSON은 전기적 특성 42행, 권장 동작 조건 3개, 동작 제약 5개를 담습니다. 정격·ESD·패키지 열 정보·핀·그래프·측정/응용 참고는 원본을 보존하고 `deferred_information`에 아직 구조화하지 않았다고 표시합니다. 이 JSON이 문서 전체 추출 완료를 뜻하지는 않습니다.

`Extractor.extract(packet)` 경계를 마련했으므로 API 연결은 이 인터페이스를 구현하는 추출기를 추가하는 방식으로 진행할 수 있습니다. API를 넣는 것만으로 정확성이 보증되는 것은 아니며, 입력 프롬프트·출력 스키마·누락/잘림 처리·회귀 평가가 필요합니다.

### 중요한 원문 정정

원본 7쪽에서 36V 정지 전류 800µA는 **MAX**, 원본 6쪽에서 dIOS/dT 10pA/°C는 **TYP**입니다. 이전 대화에서 이를 반대로 설명한 것은 잘못이었습니다. 새 수동 JSON은 원본 이미지와 단어 좌표에 맞춰 기록했습니다. 예전 36V 측정값 약 932.7µA는 최대 800µA 기준을 넘으므로, 과거 19행 전부 통과 주장은 이 기준에서는 유지할 수 없습니다. 회로 재실행은 이번 작업에 포함하지 않았습니다.

## 코드로 원본 셀 근거 추출

```powershell
python run_spec_candidates.py --run-dir runs/lm358b_overview_20261112 --code-tables
```

`spec_01_extract_rows.py`의 `NativeTableExtractor`가 원본 PDF에서 표 행 경계를 찾고, **머리글 셀의 x좌표와 숫자 단어의 위치**로 MIN/TYP/MAX를 연결합니다. PyMuPDF가 데이터의 MIN/TYP/MAX 셀을 병합해 반환해도 그 병합 셀의 배열 순서를 신뢰하지 않습니다. 페이지 번호나 LM358B의 값을 코드에 고정하지 않으며 페이지 계획과 대상 제품명을 입력받습니다.

- `06_code_table_evidence.json` / `.md`: 원본 셀의 숫자·기호·좌표·단위·조건 원문. 기존 수동 사양 JSON을 덮어쓰지 않습니다.
- 단순 숫자와 ±·음수 표기는 처리하지만, 수식·복합값은 원문을 보존하고 해석 필요로 남깁니다.
- 세로로 병합된 제품명/조건 셀은 실제 셀 범위 안에서만 연결합니다. 명시된 다른 제품 행은 분리하고 제품군 표기는 확인 대상으로 남깁니다.
- 문장 의미, 표 공통조건의 우선순위, 단위 해석과 합격 정책, 누락 없는 추출은 아직 보증하지 않습니다. 다음 단계의 원문 대조도 이 범위를 자동 해결했다고 주장하지 않습니다.

LM358B 실행에서 42행을 보존했고 LM358BA 전용 2행을 별도 분리했습니다. 38행은 단순 수치 열을 배치했고, 4행(공통모드 범위·복합 임피던스)은 해석 필요입니다. 38행의 수치 슬롯은 앞서 채팅 AI가 원본을 보고 작성한 후보와 일치했지만, 이는 독립적인 전체 정확도 검증을 대신하지 않습니다.

## 원문 대조 및 통합

```powershell
python run_spec_verification.py --run-dir runs/lm358b_overview_20261112
```

- `07_source_verification.json` / `.md`: 원본 PDF를 다시 열어 머리글·수치·단위 셀의 단어와 좌표를 대조합니다. 두 JSON은 페이지/행 위치로 연결하며 값이 같다는 이유만으로 행을 짝짓지 않습니다. 중복 연결·미연결·검증 후 입력 변경을 감지합니다.
- `08_merged_specs.json`: 코드의 원본 셀 근거와 AI의 사양명·조건·복합값 후보를 결합합니다. 각 필드의 출처/검증 상태를 유지하고 충돌 값은 비워 양쪽 원값을 별도로 보존합니다.
- 원문 수치·열 비교는 같은 PyMuPDF 엔진을 사용하므로 엔진 자체의 오독을 완전히 배제하지 못합니다. 단순 일치가 최종 정확성 보증은 아닙니다.
- 현재 수치 38행 일치, 수식·복합값 4행 해석 대기입니다. 단위는 39행 텍스트/허용 표기 일치, 잡음 단위 및 복합값 단위 3행 확인 필요입니다.
- 조건·사양 의미와 그래프/각주/전체 문서 완전성은 추가 검토가 필요하므로 `ready_for_design=false`입니다. 권장 동작 조건·동작 제약도 AI 후보로 보존하며 독립 검증 완료로 바꾸지 않습니다.

## 추가 문서 점검

OPA2134 PDF(35쪽), LM741 계열 PDF(17쪽)에도 첫 두 단계를 실행했습니다. 일반적인 `Electrical Characteristics` 제목처럼 제품명이 없는 표는 대상 외 자료로 버리지 않고 `specs_product_scope_review` 후보로 보존합니다. LM741 파일은 실제 표제가 LM741-MIL이므로 정확한 제품 변형을 확인해야 합니다.

현재 점검은 TI의 텍스트·책갈피가 있는 PDF 3개 사례입니다. 스캔본과 책갈피 없는 다양한 제조사 문서에서의 정확도를 보증하지 않습니다. 미분류 페이지를 보존하고 후속 시각 확인으로 넘기는 방식을 유지합니다. 상세 결과는 `runs/INITIAL_STAGE_CHECKS.md`에 있습니다.

## LM358B 사례

PDF가 디지털 텍스트와 책갈피를 제공하므로 가벼운 탐색만으로 6~7쪽 전기적 특성, 15~21쪽 특성 곡선, 24쪽 측정 설명, 25~26쪽 동작 설명을 찾을 수 있습니다. 4~5쪽 정격·권장 조건과 3쪽 핀도 함께 참고해야 합니다. 응용/전원 설명 27~29쪽도 참고 대상으로 남깁니다.

상세 사양표를 올바른 MIN/TYP/MAX로 추출하는 정확도는 이 탐색 단계에서 보증하지 않습니다. 그래프·회로도 해석과 복잡한 표는 후속 이미지 파싱/원문 검증 단계에서 다룹니다. 기존 31/25/42행 추출 결과나 성공 회로는 변경하지 않았습니다.
