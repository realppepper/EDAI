# 다음 하네스 개선 후보 — 반복 설계 이력 전달

후속 상태: 사용자의 구현 요청에 따라 이력 전달을 구현했다. [구현·검증 기록](HARNESS_ITERATION_HISTORY.md)을 참고한다. 아래는 변경 전 검토 기록이다.

## 확인한 현재 상태

24pF 기준 회로의58조건 재검증은 완료했다. 다음 개선은 회로·검사 기준을 바꾸기보다 설계자가 받는 정보를 개선하는 방향이다.

`harness_03_loop.py`는 후보의 회로·측정 대장·응답을 보존하지만, `prepare`에서다음 요청을 만들 때 `make_request`에 현재 회로와 해당 측정 결과만 전달한다. `harness_02_request.py`의요청에는 목표·현재 값·유효성·미해결 항목과 지침은 있으나, 여러 후보 사이의 실제 변경과 관측된 성능 변화 기록은 없다.

수치나 목표가 아예 전달되지 않는 문제는 아니다. 같은 대화에서 작업하는LLM은 별도의 대화 기억을 가질 수 있으므로 ‘LLM이 무조건 과거를 모른다’고도 말할 수 없다. 새 호출이나 새 에이전트에서도 같은 이력을 확실히 이용하도록 코드로 연결하는 것이 개선 후보이다.

## 첫 개선 가설

같은 설계 실행 안에서 실제로 변경한 소자·연결과 그 후 관측된 지표 변화를 함께 제공하면, 이미 효과가 없었거나 다른 조건을 악화시킨 수정을 반복하는 것을 줄일 수 있는가?

이를 위해 다음 요청에 최근 수정 이력을 구조화하여 추가하는 방안을 우선 검토한다.

- 실제 넷리스트 차이와LLM이 선언한 변경을 구분한다.
- 같은 사양·같은 시험 조건에서 이전 값과 새 값을 연결한다.
- 새로 통과하거나 미달한 조건, 기존 통과 항목의 악화를 표시한다.
- 측정 오류나 측정 전제 미충족의 수치는 정상적인 성능 변화로 계산하지 않는다.
- 여러 소자를 동시에 변경했으면 특정 소자가 원인이라고 확정하지 않는다.
- 동일 실행 안에서 얻은 기록만 사용한다. 기존24pF 성공값을 비교 대상에게 숨은 정답으로 제공하지 않는다.

원인 확정 실험, 최선 후보 순위 변경, 지침 자동 진화는 이번 첫 개선과 섞지 않는 편이 효과를 분리하기 좋다. 기존 고정 지침과 검사 기준은 기준선으로 보존한다.

## 검증 방법의 주의점

과거 이력은 적어도 한 번 수정하고 측정한 다음부터 생기므로, 수정안1회만 비교한 실험으로는 이 기능을 평가할 수 없다. 동일 모델·과제·측정기·수정 기회를 맞춘 여러 회차에서 비교해야 한다.

LLM이 이미 전체 대화 이력을 받는 조건과 새 요청만 받는 조건을 섞으면 해석이 어려워진다. 양쪽의 대화 이력 제공 방식을 통제해야 한다. 실제 설계 성공률·반복 횟수·기존 통과 항목 악화로 효과를 확인하고, 정보가 많아진 것만으로 성능 향상을 주장하지 않는다.

이 문서는 현재 코드 점검과 개선 제안이다. 아직 루프 코드나 지침을 변경하지 않았고, 새로운 설계·비교 실험·Git push도 실행하지 않았다.
