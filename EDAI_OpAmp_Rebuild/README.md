# EDAI — 아날로그 op amp 설계 자동화 및 피드백 시스템

이 브랜치는 다훈이 작업한 **데이터시트 사양 추출부터 회로 설계·검증·수정까지의 실행 흐름**을 공유합니다. 최종 갱신: **2026-11-18**.

목표는 사용자가 원하는 op amp 사양을 정리하고, AI가 제안한 회로를 LTspice로 검사해 부족한 부분을 반복 수정하는 것입니다. AI의 설명만으로 성공을 판단하지 않고 **실제 시뮬레이션 측정값과 미리 정한 판정 규칙**을 사용합니다. 현재는 일반 MOS 모델과25°C 조건을 중심으로 검증하며, 실제 공정 PDK를 사용한 제작 가능성까지 검증한 단계는 아닙니다.

## 처음 읽는 조원에게

- 전체 흐름과 현재 상태는 이 README부터 읽으면 됩니다.
- 설치·실행은 [설치 안내](docs/SETUP_AND_RUN.md), 파일별 역할은 [코드 지도](docs/CODE_MAP.md)를 확인하세요.
- 이번에 추가한 기능과 시험 결과는 [11월18일 변경 정리](docs/LATEST_UPDATE_20261118.md)에 모았습니다.
- `runs/`는 각 실행의 작업 공간입니다. PDF, 파형, 로그와 개인 키는 이 저장소에 포함하지 않았습니다. 저장소를 받았다고 과거 실행을 그대로 재개할 수 있는 것은 아닙니다.

## 시스템은 어떤 순서로 동작하나요?

```text
데이터시트 PDF + 대상 모델명
  → 전체 페이지를 가볍게 읽고 필요한 정보가 있는 페이지 선택
  → 해당 페이지 이미지·텍스트 파싱
  → 사양 JSON 정리 + 원문/시험 조건 대조
  → HKG와 PDG 구성
  → 설계 목표 및 검사 계획 확정
  → AI가 최초 회로 넷리스트 작성
  → LTspice 실행 → 코드가 측정·판정
  → 미달 항목·측정값·이력을 AI에 전달 → 수정 회로 재검사
  → 구현 범위 통과 시 결과·넷리스트·스케마틱 저장
```

**데이터시트는 기존 제품의 내부 구조를 그대로 복제하기 위한 자료가 아닙니다.** 전원, 부하, 입력 조건과 함께 성능 목표를 정하는 참고 자료입니다. 추출한 정격·권장 동작 조건·typical 수치를 모두 같은 종류의 합격 기준으로 쓰지 않으며, 목표 선택 정책에서 사용할 항목과 해석을 명시합니다.

| 단계 | 하는 일 | 주로 볼 파일 |
|---|---|---|
| PDF 읽기 | PyMuPDF로 페이지와 텍스트를 확인하고 선택 페이지를 이미지로 준비합니다. NVIDIA Nemotron Parse로 레이아웃을 읽습니다. | `run_pdf_overview.py`, `run_pdf_layout.py`, `pdf_01`~`pdf_05` |
| 사양 정리·대조 | 코드가 확실하게 읽을 수 있는 표 행·수치·단위를 정리하고, AI가 조건 의미를 보완합니다. 원문 근거와 누락/해석 검토를 남깁니다. | `run_spec_pipeline.py`, `spec_01`~`spec_03` |
| HKG(하드웨어 지식 그래프) | 사양값과 시험 조건, 대상 모델, 원문 출처를 연결합니다. 추출 정보를 추적하기 위한 구조입니다. | `run_hkg.py`, `hkg_01_build.py` |
| PDG(포트 의존성 그래프) | 포트·신호 관계와 인가 순서, 필요한 지연/선행 조건을 정리합니다. 명시한 검사 정책으로 적용합니다. | `run_pdg.py`, `pdg_01`~`pdg_05` |
| 검사 계획 | 채택한 목표를 어느 전원·부하·입력 조건에서 어떤 방법으로 측정할지 정의합니다. SPICE 테스트벤치는 회로와 함께 구성됩니다. | `run_measurement_plan.py`, `plan_01`~`plan_04` |
| 회로 설계·수정 | AI에 목표·검사 방법·설계 지침·과거 결과를 전달하고, 최초/수정 넷리스트를 받습니다. | `run_datasheet_design.py`, `run_fixed_harness_loop.py` |
| 실제 검증 | 기동, DC/AC/과도 응답 등을 실행하고 측정합니다. 시험 조건과 생성된 SPICE가 같은지도 독립적으로 대조합니다. | `run_verification_pipeline.py`, `verify_*`, `validation_*` |
| 이력·최선 후보 | 실패/오류/미검증을 구분하고 이전 통과 조건의 퇴행을 확인합니다. 결과·근거·수정 이력을 보존합니다. | `harness_03_loop.py`, `harness_05_history.py`, `harness_07_workflow.py` |

표의 짧은 파일명은 별도 표시가 없으면 `opamp_pipeline/` 아래에 있습니다. 순서가 있는 파일 이름을 따라 읽으면 각 단계의 책임을 확인할 수 있습니다.

## 코드, AI, LTspice는 무엇을 맡나요?

| 담당 | 역할 |
|---|---|
| Python 코드 | 입력/단위/출처 검사, 실행 순서 관리, 테스트벤치 생성, 시뮬레이터 호출, 파형 측정, 합격 판정, 이력/해시 보존 |
| AI | 문서 의미 검토, 회로 구조·소자값 제안, 미달 원인에 대한 가설과 수정 방향 제안, 필요한 참고자료 선택 |
| LTspice | 주어진 모델과 시험 조건으로 회로를 수치 해석해 파형·측정 근거 생성 |

**현재 설계용 LLM API는 연결하지 않았습니다.** 채팅/에이전트가 AI 역할을 맡아 코드가 만든 `REQUEST`를 읽고 `RESPONSE` JSON을 제공합니다. 이를 파일로 넘기면 코드가 검증과 다음 단계를 진행합니다. 문서 파싱용 NVIDIA API와 선택 기능인 IEEE MCP는 별도입니다. API를 연결하기 전에는 PDF를 넣는 것만으로 모든 AI 판단 단계가 무인 완료되지는 않습니다.

AI가 말한 실패 원인은 가설입니다. 코드는 측정값과 판정의 유효성을 확인하지만, 그 물리적 원인이 맞다는 것까지 자동 증명하지는 않습니다. 모델이 표현하지 못하는 특성은 시뮬레이션을 실행했더라도 통과로 선언하지 않습니다.

## 하네스, 하네스², Optuna는 무엇이 다른가요?

- **하네스:** AI가 참고하는 설계 지침과 도구 사용 규칙, 검사 결과·이력을 전달하는 환경입니다. 단순한 설계 요청에 비해 목표·검사 방법·제약·경험을 명시적으로 제공합니다.
- **하네스²:** 현재 회로의 값만 고치는 데 더해, 이후 설계에 사용할 지침 변경안도 시험하고 채택 여부를 판정하는 선택 경로입니다. 연결은 구현했지만 항상 성능을 높인다는 근거는 아직 없습니다.
- **Optuna:** 연결 구조는 유지한 채 선택한 R/C 값이나 MOS의 W/L을 숫자로 탐색하는 선택 기능입니다. AI가 변수와 범위를 제안하고 코드가 제한과 예산을 검사합니다. 새 연결 구조가 필요하면 AI가 맡습니다.

Optuna는 기본적으로 꺼져 있습니다. 켰더라도 모든 실패에서 반드시 호출되는 것은 아닙니다. 유효한 수치 미달이나 완전한 파형으로 확인한 기동 미달이 있어야 하며, AI가 직접 수정하는 경로도 남아 있습니다. 측정 오류·누락을 물리적 미달 점수로 바꾸지 않습니다. 부분 선별 결과가 좋아도 원래 전체 검사로 확인한 뒤에만 성공을 판정합니다. 자세한 사용법은 [Optuna 안내](docs/OPTUNA_SIZING.md), 지침 개선은 [하네스² 안내](docs/HARNESS2_EVOLUTION.md)를 보세요.

IEEE와 데이터시트 참고자료도 항상 전부 전달하지 않습니다. 필요를 명시한 경우 선택한 내용을 출처와 함께 전달하도록 구성했습니다.

## 지금까지 어디까지 확인했나요?

| 확인 내용 | 결과와 의미 |
|---|---|
| 데이터시트부터 설계 루프 | LM358B와 TL071C 사례를 진행했습니다. 여러 제조사·다양한 op amp에 대한 충분한 일반화 검증은 아직 아닙니다. |
| 최신 LM358B 연결 확인 | **80개 사양 조건 중58개 통과,22개 미검증**, 별도의 **기동5개 전원점 통과**. 이는 해당 검사 계획과 일반 모델에서 구현한 범위의 통과입니다. |
| Optuna 연결 보완 | 기동 보완 제안, 부분 선별 밖의 미달 처리, 전체 검사 기반 후보 선택, 전력 동률 처리와 저장·재개를 확인했습니다. |
| 코드 회귀 검사 | 로컬 원본에서 **418개 통과**. 공유본의 통과/생략 개수는 [공유본 검사 기록](docs/SHARE_MANIFEST.json)에 별도로 기록합니다. |
| 효과 비교 | 하네스/하네스² 및 Optuna의 안정적인 성공률·반복 수·시간·토큰 이점은 아직 입증하지 않았습니다. |

**미검증22개는 이미 분류했습니다.**15개는 모델 미검증,7개는 어댑터 미검증으로 기록됩니다. 단일 채널이라 평가할 수 없는 채널 분리, 보정되지 않은 잡음·입력 전류 등 모델/구조 한계가 포함되므로 단순히 검사 함수22개를 더 만들면 해결되는 문제가 아닙니다. 추후 목적에 맞는 모델·측정 방법을 함께 검토해야 합니다.

기동 검사는 전원을 올렸을 때 실제 동작 상태로 안정되는지 보는 별도 요구사항입니다. 따라서58개 성능 조건을 통과해도 기동 실패라면 완료로 판정하지 않습니다. 미검증은 실패와도 다르며, 전체 제조사 사양을 달성했다고 표시하지 않습니다.

과거 예시에는 확대 정책의74개 구현 조건+29개 미검증,기동7개 전원점 결과도 있습니다. **검사 계획이 다르므로 최신58/80과 통과율을 직접 비교하면 안 됩니다.** 조건 수는 모델명만으로 고정되는 값이 아닙니다.

## 현재 남은 과제

| 과제 | 현재 부족한 점 | 다음에 확인할 것 |
|---|---|---|
| **다른 데이터시트·구조에서 일반화** | LM358B 중심의 경험이 많고 다른 제품 사례가 적습니다. | 제조사/형식/전원 범위가 다른 op amp에서 추출부터 설계까지 실행하고 제품별 예외를 줄입니다. |
| **미검증 성능의 범위 확장** | 잡음, 입력 전류, 채널 분리 등은 일반 모델과 단일 채널 구조로 판정하기 어렵습니다. | 지원 모델·어댑터와 평가 가능 범위를 정한 뒤 개별적으로 검증합니다. PDK는 현재 도입하지 않았습니다. |
| **하네스·하네스² 효과 평가** | 기능은 연결했지만 이점이 일관되게 검증되지 않았습니다. | 같은 모델/초기 과제/예산으로 기본 피드백과 비교하고 악화·무효 사례도 포함합니다. |
| **Optuna의 실제 이점 확인** | 연결과 작은 시험은 했으나 LLM 단독보다 유리하다고 결론내릴 수 없습니다. 이전 비교에서는 실제 호출되지 않은 경우도 있었습니다. | 호출된 경우와 아닌 경우를 구분하고 변수·범위·시행 예산을 통제해 비교합니다. |
| **추출·검사의 신뢰성 유지** | 현재 형식과 조건을 넘어서는 모든 문서/해석을 보장하지 않습니다. | 다른 문서, 잘못된 입력, 누락, 재시도/캐시에서 조용히 통과하는 오류가 없는지 확대 점검합니다. |
| **설계 API와 토큰 기록 연결** | 설계 AI는 채팅/에이전트가 대신하고 실제 토큰/비용 비교는 하지 않았습니다. | 모델 확정 후 요청·응답을 API에 연결하고 토큰/비용·시간을 같은 형식으로 기록합니다. |
| **팀 UI·블록 조합 통합** | 이 브랜치의 설계 루프와 다른 조원의 UI/블록 방식은 아직 미통합입니다. | 사양·회로·측정 결과의 공통 입출력을 정하고 실제 실행 상태를 UI와 연결합니다. |

우선순위는 **현재 검사·루프의 안정성을 유지하면서 다른 op amp 사례를 늘리는 것**입니다. 효과 비교의 추가 확대, PDK, 별도 검증 LLM과 spicelib 도입은 후속 검토 사항이며 이번 갱신에서 새로 구현하지 않았습니다.

## 설치하고 무엇부터 해보면 되나요?

Windows·Python3.12·LTspice 환경에서 확인했습니다. 프로젝트 폴더에서 실행하세요.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -q
```

기본 테스트는 API나 실제 전체 회로 설계 실행을 대신하지 않습니다. 개인 PDF/실행 자료가 없는 검사는 생략될 수 있습니다. 선택 기능은 별도로 설치합니다.

```powershell
# 숫자 탐색을 사용할 때만
.\.venv\Scripts\python.exe -m pip install -r requirements-optuna.txt
# IEEE MCP를 사용할 때만
.\.venv\Scripts\python.exe -m pip install -r requirements-ieee.txt
```

`.env.example`을 참고해 로컬 `.env`에 키를 설정하세요. 키를 저장소에 올리지 않습니다. PDF와 LTspice도 직접 준비해야 합니다. 새 문서로 시작하는 방법은 [최초 설계 안내](docs/COLD_START.md), 검증·수정의 반복은 [운영 루프](docs/CONTINUOUS_WORKFLOW.md)를 따라가세요. 새 문서에서 이전 목표·전원점·출처 해시를 그대로 가져오면 안 됩니다.

| `runs/` (Git 제외) | 실행별 JSON, 넷리스트, 측정 데크, 파형·로그·검사 근거 |

회로 본체는 `.inc` 넷리스트로 저장하고, 테스트벤치가 이를 불러 시뮬레이션합니다. 통과 시 `.asc` 스케마틱도 생성합니다. 스케마틱 생성/연결 대조가 완료됐다는 것과 실제 공정·레이아웃 검증까지 끝났다는 것은 구분해야 합니다.
